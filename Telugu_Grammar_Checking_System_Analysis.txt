# Complete Telugu Grammar Checking System Analysis

## 1. High-Level System Flow

### The Complete Journey: User Input -> API -> Processing -> Output

```
User sends Telugu sentence
        |
        V
FastAPI receives HTTP POST request at /autocorrect
        |
        V
Pydantic validates and normalizes input (NFC Unicode)
        |
        V
Tokenization with character offset tracking
        |
        V
Word boundary recovery (splits joined words)
        |
        V
Subject-verb agreement correction
        |
        V
Postposition insertion
        |
        V
Grammar rule engine application
        |
        V
Spell checking with N-gram re-ranking
        |
        V
Error collection and span generation
        |
        V
JSON response with corrections and highlighting data
        |
        V
Frontend uses offsets to highlight errors in original text
```

### Where FastAPI Receives Input
- **Entry Point**: main.py creates FastAPI app with CORS middleware
- **Route Handler**: app/routes/autocorrect.py handles POST /autocorrect
- **Input Validation**: app/models.py defines AutocorrectRequest with automatic Unicode normalization
- **Health Check**: main.py provides /health endpoint to verify system status

### What Happens in Each Stage
1. **Tokenization**: Splits text while preserving character positions
2. **Boundary Recovery**: Fixes incorrectly joined Telugu words
3. **Agreement Correction**: Ensures verbs match subject pronouns
4. **Postposition Insertion**: Adds missing grammatical markers
5. **Grammar Rules**: Applies pattern-based corrections
6. **Spell Check**: Corrects typos using multiple scoring factors
7. **Response Generation**: Builds structured JSON with corrections

### How Final Response is Formed
- **Corrected Sentence**: Reconstructed from processed tokens
- **Error Spans**: Array of corrections with start/end positions
- **Metadata**: Error types, explanations, and processing stages
- **UI Integration**: Frontend uses spans to highlight specific text regions

## 2. Pipeline Breakdown (Stage-by-Stage)

### Stage 1: Tokenization

**File**: app/routes/autocorrect.py (lines 22-40)

**How sentence is split**:
```python
regex = re.compile(r'([\u0C00-\u0C7F]+|[a-zA-Z]+|[0-9]+|[^\s\u0C00-\u0C7Fa-zA-Z0-9]+|\s+)')
```

**What this regex does**:
- [\u0C00-\u0C7F]+ - Captures Telugu words (continuous Telugu characters)
- [a-zA-Z]+ - Captures English words  
- [0-9]+ - Captures numbers
- [^\s\u0C00-\u0C7Fa-zA-Z0-9]+ - Captures punctuation/symbols
- \s+ - Captures whitespace blocks

**How start/end offsets are stored**:
```python
parts = []           # Actual text fragments
part_spans = []      # (start, end) character positions
token_indices = []   # Which parts are actual tokens (not spaces)
tokens = []          # Just the token text
```

**Why offsets are important**:
- Enable precise error highlighting in UI
- Allow reconstruction of corrected text
- Maintain mapping between original and corrected positions
- Essential for multi-stage processing where token count may change

### Stage 4: Grammar Rule Engine

**File**: app/core/grammar_engine.py

**How rules are loaded**:
```python
def __init__(self, rules: List[Dict]):
    self.rules: List[Dict] = []
    for r in rules:
        rr = dict(r)
        pat_src = str(rr.get("pattern", "")).strip()
        rr["_priority"] = int(rr.get("priority", 100))
        
        # Determine rule scope
        is_sentence = bool(re.search(r"\s", pat_src)) or pat_src.startswith("^") or pat_src.endswith("$")
        rr["_scope"] = "sentence" if is_sentence else "token_suffix"
        rr["_pat"] = re.compile(pat_src) if is_sentence else re.compile(pat_src + "$")
```

**Difference between rule types**:

**Token-level rules**:
- Apply to individual words
- Pattern automatically gets "$" appended (word boundary)
- Example: "????" matches exact word "????"

**Sentence-level rules**:
- Contain whitespace or anchors (^/$)
- Apply to whole sentence or multi-word patterns
- Example: "????.*????????" matches subject-verb patterns

**How priority works**:
- Lower numbers run first (default: 100)
- Allows fine-grained control over rule application order
- Prevents conflicts between similar rules

**How rules are applied**:
```python
for rule in sorted(self.rules, key=lambda r: r["_priority"]):
    if rule["_scope"] == "token_suffix":
        # Apply to each token
        for token in tokens:
            if rule["_pat"].search(token):
                # Apply correction
    else:
        # Apply to whole sentence
        if rule["_pat"].search(sentence):
            # Apply correction
```

### Stage 5: Clause Detection (Advanced Feature)

**File**: app/core/clause_processor.py and app/core/clause_grammar_checker.py

**How clauses are identified**:
Clauses are detected using:
- **Verb forms and tense markers**: Endings that indicate clause boundaries
- **Conjunctions**: Words like "?????", "??????", "????????"
- **Particles and morphological endings**: Grammatical markers
- **NOT by word position** (Telugu has free word order)

**Clause Types**:
```python
class ClauseType(Enum):
    INDEPENDENT = "independent"              # Complete meaning
    NON_FINITE_PARTICIPIAL = "non_finite"    # Participial forms
    INFINITIVAL = "infinitival"              # Purpose/intent
    CONDITIONAL = "conditional"              # "If then" type
    SEQUENTIAL = "sequential"                # Explanatory
    RELATIVE = "relative"                    # Relative clause
    TEMPORAL = "temporal"                    # When/time-based
```

**How clauses are stored**:
```python
@dataclass
class ClauseUnit:
    tokens: List[str]

    end_idx: int

```

### Stage 6: Spell Checking with N-gram Re-ranking

**File**: app/core/spellchecker.py

**How spell checking works**:
1. **Candidate Generation**: Uses Levenshtein distance to find similar words
2. **Phonetic Scoring**: Considers sound-alike substitutions
3. **Frequency Ranking**: Prefers common words
4. **Context Re-ranking**: Uses bigram probabilities when context available

**Scoring Formula**:
```python
base_score = FREQ_W × norm_freq + PHONETIC_W × phonetic_sim + LENGTH_PENALTY
final_score = base_score + NGRAM_W × ngram_boost
```

### Stage 7: Error Collection & Offsets

**File**: app/routes/autocorrect.py (lines 70-131)

**How errors are stored**:
```python
@dataclass

    start: int           # Character position in original text
    end: int             # Character position end
    original: str        # Original text
    correction: str      # Corrected text

```

**How positions are tracked**:
- **Original spans**: From tokenization stage
- **Token mapping**: Links token indices to character positions
- **Boundary recovery**: Handles cases where token count changes
- **Multi-stage tracking**: Records which stages modified each token

**How overlapping errors are handled**:
- **Stage tracking**: Each modification records its stage
- **Sequential application**: Later stages can override earlier ones
- **Span accumulation**: Multiple corrections can be stored for same region

## 4. Data Flow Between Files

### Step-by-Step Chain of Execution

```
User Request
    |
    V
FastAPI (main.py)
    |
    V
Route Handler (app/routes/autocorrect.py)
    |
    V
Unicode Utils (app/core/unicode_utils.py) - Tokenization
    |
    V
Boundary Recovery (app/core/boundary_recovery.py) - Word splitting
    |
    V
Agreement & Postposition (app/core/agreement_postposition.py) - Grammar fixes
    |
    V
Grammar Engine (app/core/grammar_engine.py) - Rule-based corrections
    |
    V
Spell Checker (app/core/spellchecker.py) - Typo correction
    |   |-- Levenshtein (app/core/levenshtein.py) - Edit distance
    |   |-- Phonetic (app/core/phonetic.py) - Sound similarity
    |   |-- N-gram (app/core/ngram.py) - Context scoring
    |
    V
Response Assembly (app/routes/autocorrect.py)
    |
    V
JSON Response with Models (app/models.py)
```

### Detailed Data Flow

**1. Request Reception**
- main.py receives HTTP POST at /autocorrect
- app/models.py validates input using AutocorrectRequest
- Data flows as: JSON -> Pydantic model -> validated string

**2. Tokenization**
- autocorrect.py calls unicode_utils.py
- unicode_utils.py uses regex to split text
- Data flows as: string -> token list + character spans
- Example: "???? ??????" -> ["????", "???????"] + [(0,3), (4,9)]

**3. Boundary Recovery**
- autocorrect.py calls boundary_recovery.py
- boundary_recovery.py checks dictionary and tries splits
- Data flows as: tokens -> recovered tokens (possibly more)
- Example: ["???????????"] -> ["?????", "???????"]

**4. Agreement Correction**
- autocorrect.py calls agreement_postposition.py
- agreement_postposition.py detects subjects and fixes verbs
- Data flows as: tokens -> corrected tokens + error list
- Example: ["????", "???????"] -> ["????", "???????"] + errors

**5. Grammar Rules**
- autocorrect.py calls grammar_engine.py
- grammar_engine.py applies JSON rules to tokens
- Data flows as: tokens -> grammar-checked tokens + more errors
- Example: Applies pattern-based corrections

**6. Spell Checking**
- autocorrect.py calls spellchecker.py
- spellchecker.py orchestrates multiple components:
  - levenshtein.py: Generates candidate words
  - phonetic.py: Scores phonetic similarity
  - ngram.py: Provides contextual probabilities
- Data flows as: word + context -> suggestions with scores
- Example: "???????" + ["????"] -> [("???????", 0.95)]

**7. Response Assembly**
- autocorrect.py collects all corrections
- Maps token positions back to character spans
- Builds response using models.py classes
- Data flows as: corrections + spans -> JSON response

## 6. Design Decisions

### Why Rule-Based?

**The Choice**: The system primarily uses rule-based grammar correction rather than machine learning.

**Why This Makes Sense**:
1. **Interpretability**: Each correction can be explained with specific rules
2. **Control**: Developers can precisely tune which corrections are made
3. **Data Efficiency**: Doesn't require massive labeled datasets for Telugu
4. **Reliability**: Consistent behavior, no "black box" decisions
5. **Maintenance**: Easy to add new rules without retraining models

**Trade-offs**:
- **Pros**: Precise, explainable, maintainable
- **Cons**: Limited to known patterns, requires manual rule creation

**Example**: Instead of training a model to detect subject-verb agreement, the system has explicit rules:
```python
if subject == "????" and verb_ending == "?????":
    change_ending_to("?????")
```

### Why Offsets?

**The Choice**: Character-level start/end positions for error highlighting.

**Why This Works**:
1. **UI Integration**: Direct mapping to text editor positions
2. **Precision**: Exact character ranges for highlighting
3. **Language Agnostic**: Works with any script including Telugu
4. **Reconstruction**: Can rebuild corrected text from spans
5. **Multi-stage**: Survives multiple processing stages

**Technical Implementation**:
```python
# Tokenization tracks positions
parts = ["????", " ", "????", " ", "???????"]
part_spans = [(0,3), (3,4), (4,8), (8,9), (9,14)]

# Corrections reference original positions
span = {
    "start": 4, "end": 8,  # "????" in original text
    "original": "????",
    "correction": "??????"
}
```

### Why Staged Pipeline?

**The Choice**: Sequential processing stages rather than monolithic correction.

**Why This Architecture**:
1. **Modularity**: Each stage has clear responsibility
2. **Debugging**: Can isolate issues to specific stages
3. **Extensibility**: Easy to add new processing stages
4. **Quality Control**: Each stage can validate previous work
5. **Performance**: Early stages can reduce work for later ones

**Pipeline Benefits**:
```
Stage 1: Tokenization -> Clean input for all stages
Stage 2: Boundary Recovery -> Fixes obvious issues first  
Stage 3: Agreement -> Handles grammatical structure
Stage 4: Grammar Rules -> Applies pattern-based fixes
Stage 5: Spell Check -> Final polish with context
```

### Why Separate Modules?

**The Choice**: Many small, focused files rather than few large ones.

**Advantages**:
1. **Single Responsibility**: Each file has one clear purpose
2. **Testing**: Can test individual components in isolation
3. **Reusability**: Components can be used in different contexts
4. **Maintainability**: Easier to understand and modify
5. **Collaboration**: Multiple developers can work on different modules

**Example Separation**:
- spellchecker.py - Only spell checking logic
- grammar_engine.py - Only grammar rule processing  
- agreement_postposition.py - Only subject-verb agreement
- boundary_recovery.py - Only word boundary detection

### Why Unicode-Normalization?

**The Choice**: Automatic NFC normalization in Pydantic models.

**Importance for Telugu**:
1. **Consistency**: Multiple Unicode representations can look identical
2. **Correctness**: Prevents false mismatches due to encoding differences
3. **Interoperability**: Standardized representation across systems
4. **Performance**: Consistent data improves algorithm efficiency

**Example**:
```python
# Both look identical but have different byte representations
text1 = "????"  # NFC normalized
text2 = "????"  # NFD normalized (decomposed)

# Normalization makes them identical
normalized = unicodedata.normalize("NFC", text2)
```

### Why Grapheme Clusters?

**The Choice**: Process Telugu text as grapheme clusters rather than characters.

**Why Critical for Telugu**:
1. **Conjunct Consonants**: "???" should be one unit, not three characters
2. **Matra Attachments**: "??" (consonant + vowel sign) is one logical unit
3. **Edit Distance**: More accurate similarity measurements
4. **User Perception**: Matches how users actually see the text

**Example**:
```python
"????" -> ["??", "?"]  # 2 grapheme clusters
"????" -> ["?", "?", "?", "?"]  # 4 Unicode characters
```

## 7. Strengths and Limitations

### Strengths

#### 1. **Comprehensive Pipeline**
- **What works well**: Complete end-to-end processing from raw text to corrections
- **Why it's good**: Handles multiple error types in single API call
- **Example**: Fixes agreement, postpositions, grammar rules, and spelling together

#### 2. **Telugu-Specific Design**
- **What works well**: Deep understanding of Telugu morphology and grammar
- **Why it's good**: Not just generic NLP applied to Telugu
- **Example**: Handles complex verb conjugations and postposition systems

#### 3. **Context-Aware Processing**
- **What works well**: Uses N-gram models for contextual spell checking
- **Why it's good**: Better suggestions based on surrounding words
- **Example**: "????" -> suggests "????????" because of subject context

#### 4. **Precise Error Highlighting**
- **What works well**: Character-level offsets for UI integration
- **Why it's good**: Exact positioning for user-friendly corrections
- **Example**: Can highlight specific characters that need correction

#### 5. **Modular Architecture**
- **What works well**: Clean separation of concerns
- **Why it's good**: Easy to maintain, test, and extend
- **Example**: Can add new grammar rules without touching spell checking

#### 6. **Performance Optimization**
- **What works well**: Efficient data structures (Trie, N-gram caching)
- **Why it's good**: Fast response times even with large dictionaries
- **Example**: Prefix search in O(k) time where k is prefix length

#### 7. **Mixed Language Support**
- **What works well**: Handles Telugu-English code switching
- **Why it's good**: Reflects real-world usage patterns
- **Example**: "???? school ?? ??????" works correctly

### Limitations

#### 1. **Rule Coverage**
- **Limitation**: Only catches errors explicitly programmed in rules
- **Impact**: Misses novel or rare error patterns
- **Example**: New grammatical constructions won't be recognized

#### 2. **Dictionary Dependency**
- **Limitation**: Spell checking limited to words in dictionary
- **Impact**: Can't handle neologisms, proper names, or technical terms
- **Example**: "????????" (optical) might be flagged as incorrect

#### 3. **Context Window**
- **Limitation**: N-gram model only considers immediate neighbors
- **Impact**: Long-distance dependencies are missed
- **Example**: Agreement errors across clause boundaries may be missed

#### 4. **Training Data Bias**
- **Limitation**: Dictionary and N-gram frequencies reflect training corpus
- **Impact**: May favor formal/written Telugu over spoken dialects
- **Example**: Regional variations might be "corrected" incorrectly

#### 5. **Complex Sentence Handling**
- **Limitation**: Clause-level processing is basic
- **Impact**: Struggles with complex multi-clause sentences
- **Example**: Nested clauses or long-distance dependencies

#### 6. **No Learning Capability**
- **Limitation**: System doesn't learn from user corrections
- **Impact**: Repeated errors aren't automatically recognized
- **Example**: If users consistently reject a suggestion, system doesn't adapt

#### 7. **Performance with Large Texts**
- **Limitation**: Designed for sentence-level processing
- **Impact**: May be slow with paragraph or document-level input
- **Example**: Processing entire essays could be time-consuming

### Improvement Opportunities

#### 1. **Machine Learning Integration**
- **What**: Add ML models alongside rule-based system
- **Why**: Catch patterns not covered by explicit rules
- **How**: Use rules for high-precision cases, ML for coverage

#### 2. **User Feedback Loop**
- **What**: Learn from accepted/rejected corrections
- **Why**: Improve suggestion quality over time
- **How**: Track correction patterns and adjust weights

#### 3. **Enhanced Context**
- **What**: Larger context windows and discourse analysis
- **Why**: Better handle long-distance dependencies
- **How**: Document-level analysis and coreference resolution

#### 4. **Domain Adaptation**
- **What**: Specialized dictionaries and rules for different domains
- **Why**: Handle technical, legal, medical Telugu
- **How**: Configurable rule sets and domain-specific vocabularies

#### 5. **Performance Optimization**
- **What**: Caching, parallel processing, streaming
- **Why**: Handle larger texts efficiently
- **How**: Async processing and result streaming

#### 6. **Better Error Explanation**
- **What**: More detailed, educational error messages
- **Why**: Help users understand *why* corrections are needed
- **How**: Link to grammar rules and examples
